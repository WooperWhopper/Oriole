# Data Models

> Read for any task touching content shape, user progress, storage, or the content JSON.  
> Always alongside `CLAUDE.md` and `docs/architecture.md`.

---

## Two kinds of data

- **Content** — read-only, bundled in `assets/content/korean.json`, generated at build time. Defines every item the app can show.
- **User progress** — mutable, stored locally via AsyncStorage. One record per encountered item, plus aggregate stats.

---

## TypeScript types — the enforced source of truth

These live in **`src/types.ts`** and are imported everywhere. The annotated JSON examples in the sections below show example values and field meanings; *these types are the contract* Claude Code must satisfy. Keep them strict — avoid `any`.

```typescript
// src/types.ts

export type Tier = 'jamo' | 'geulja' | 'word' | 'phrase';
export type ItemState = 'new' | 'learning' | 'automatic';

// ── Content (read-only, from korean.json) ───────────────────────────────
export interface Geulja {
  hangul: string;
  romanization: string;        // pronunciation-based Revised Romanisation
}

export interface ContentItem {
  id: string;                  // prefix by tier: j_ g_ w_ p_
  tier: Tier;
  hangul: string;              // the stimulus
  romanization: string;        // pronunciation-based (e.g. 국물 → "gungmul")
  meaning: string | null;      // display-only, never tested; may be null
  order: number;               // rough difficulty/frequency order within tier
  geulja?: Geulja[];           // WORD items only — drives the introduction view
  distractorIds: string[];     // >= 3 ids of confusable same-tier items
}

export interface ContentFile {
  version: string;
  language: 'ko';
  items: ContentItem[];
}

// ── User progress (mutable, AsyncStorage) ───────────────────────────────
export interface ItemRecord {
  itemId: string;
  state: ItemState;
  reps: number;                // recognition reps (introduction steps don't count)
  correctCount: number;
  incorrectCount: number;
  introduced: boolean;         // word-only: introduction completed?
  lastReactionTimeMs: number | null;
  bestReactionTimeMs: number | null;
  fastCorrectStreak: number;   // consecutive correct-AND-fast reps; gate to "automatic"
  interval: number;            // SRS interval, days
  easeFactor: number;          // SRS ease, min 1.3
  nextDue: string | null;      // ISO datetime
  lastSeen: string | null;     // ISO datetime
}

export interface SpeedPoint {
  date: string;                // YYYY-MM-DD or ISO
  medianReactionMs: number;
}

export interface EndgamePoint {
  date: string;
  wpm: number;
  tier: Tier;
}

export type AutomaticByTier = Record<Tier, number>;

export interface ProgressMeta {
  currentStreakDays: number;
  lastActiveDate: string | null;   // YYYY-MM-DD, local
  sessionsCompleted: number;
  speedHistory: SpeedPoint[];      // the hero metric over time
  endgameHistory: EndgamePoint[];
  automaticByTier: AutomaticByTier;
  currentTier: Tier;               // tier new items are drawn from
}

export interface Settings {
  soundEnabled: boolean;
  sessionLength: number;           // max items per session
}

// ── Runtime value (not persisted) ───────────────────────────────────────
export interface DrillResult {
  correct: boolean;
  reactionTimeMs: number;
}
```

The annotated examples that follow mirror these types with example values and per-field notes.

## Content schema (`assets/content/korean.json`)


Generated by the build pipeline (`docs/content-pipeline.md`). A single object with the items grouped by tier, or a flat array of `ContentItem`s with a `tier` field — flat is simpler to index, so use a flat array:

```jsonc
{
  "version": "1.0.0",
  "language": "ko",
  "items": [ /* ContentItem[] */ ]
}
```

### ContentItem

```jsonc
{
  "id": "w_jeongwon",          // stable unique id; prefix by tier: j_ (jamo) g_ (geulja) w_ (word) p_ (phrase)
  "tier": "word",              // "jamo" | "geulja" | "word" | "phrase"
  "hangul": "정원",             // what is shown as the stimulus
  "romanization": "jeong-won", // PRONUNCIATION-based Revised Romanisation (sound-change rules applied)
  "meaning": "garden",         // OPTIONAL — shown in reveal + collection, never tested. May be null.
  "order": 142,                // rough difficulty/frequency order within the tier (exact ranking not important)

  // Word-only: constituent geulja for the introduction view (docs/drill-engine.md)
  "geulja": [
    { "hangul": "정", "romanization": "jeong" },
    { "hangul": "원", "romanization": "won" }
  ],

  // Precomputed confusable distractors (ids of other items, same tier). See content-pipeline.md.
  "distractorIds": ["w_jangwon", "w_jeongmun", "w_cheongwon", "w_jeongwon2"]
}
```

Notes:
- `romanization` MUST reflect pronunciation, not spelling (e.g. 국물 → "gungmul", 같이 → "gachi"). The build pipeline guarantees this; see `docs/content-pipeline.md`.
- `geulja` is present only on `word` items (and is what the introduction view walks through). Jamo/geulja/phrase items omit it.
- `distractorIds` holds at least 3 ids (so 4 options total with the answer). The runtime resolves them to full items for their romanisations.
- `meaning` is optional and never affects scoring.

## User progress

### ItemRecord (one per encountered item)

```jsonc
{
  "itemId": "w_jeongwon",
  "state": "learning",          // "new" | "learning" | "automatic"
  "reps": 3,                    // total times drilled (recognition reps)
  "correctCount": 2,
  "incorrectCount": 1,
  "introduced": true,           // word-only: has the geulja-by-geulja introduction been completed?
  "lastReactionTimeMs": 1340,   // most recent correct-answer reaction time
  "bestReactionTimeMs": 1120,   // fastest correct reaction time so far
  "fastCorrectStreak": 2,       // consecutive correct-AND-fast reps; the gate to "automatic" (see docs/srs.md)
  "interval": 6,                // SRS interval in days
  "easeFactor": 2.5,            // SRS ease (min 1.3)
  "nextDue": "2026-06-09T00:00:00.000Z", // ISO; when this item is due for review
  "lastSeen": "2026-06-03T18:00:00.000Z"
}
```

State meaning:
- **new** — seen 0 times in a drill (or introduced but not yet recognition-drilled). Will be drilled soon.
- **learning** — drilled, not yet consistently fast. Resurfaces frequently.
- **automatic** — recognised correctly *and quickly* (under the tier's speed threshold) consistently. Reviewed rarely to confirm retention.

`introduced` applies only to words: it gates whether the next encounter is the introduction view or the whole-word recognition drill. (See `docs/drill-engine.md`.)

### ProgressMeta (single aggregate record)

```jsonc
{
  "currentStreakDays": 3,
  "lastActiveDate": "2026-06-03",       // YYYY-MM-DD, local
  "sessionsCompleted": 12,

  // Reading-speed history — the hero metric. One point per session (or per day).
  "speedHistory": [
    { "date": "2026-05-20", "medianReactionMs": 2100 },
    { "date": "2026-06-03", "medianReactionMs": 1280 }
  ],

  // Endgame capstone results (connected-text words-per-minute over time)
  "endgameHistory": [
    { "date": "2026-06-01", "wpm": 28, "tier": "word" }
  ],

  // Per-tier counts of items reached "automatic" (derivable, but cached for the dashboard)
  "automaticByTier": { "jamo": 40, "geulja": 180, "word": 95, "phrase": 0 },

  "currentTier": "word"                  // the tier new items are currently drawn from
}
```

The **"words you can now read"** collection (dashboard) is *derived*, not separately stored: filter `ItemRecord`s where `state === "automatic"` and the item's `tier === "word"`, then join to content for hangul + romanisation + meaning.

## Storage layout (AsyncStorage)

Small scale (≤ a couple thousand records), so keep it simple. Two keys:

```
oriole:records   → JSON map { itemId: ItemRecord }   // all encountered items
oriole:meta      → JSON ProgressMeta
oriole:settings  → JSON Settings                      // optional, see below
```

`profile.ts` loads `oriole:records` and `oriole:meta` into memory at startup, mutates in memory during a session, and writes back in a batch at session end (and on a safety interval). Do not write per-answer.

(If the record count ever grew large enough that loading everything is a problem — it won't at this scale — the upgrade path is expo-sqlite with a `records` table queryable by `nextDue`. Not needed for v1.)

### Settings (minimal, v1)

```jsonc
{
  "soundEnabled": true,
  "sessionLength": 20            // max items per session (tunable)
}
```

## Constants

### Tiers (`src/constants/tiers.ts`)

```javascript
export const TIERS = ['jamo', 'geulja', 'word', 'phrase']; // climb order
```

### Speed thresholds (`src/constants/thresholds.ts`)

The reaction time (ms) under which a correct answer counts toward "automatic." **Placeholders — tuned from real data near release** (see `Oriole_v1_Spec.md` §4).

```javascript
export const AUTOMATIC_THRESHOLD_MS = {
  jamo: 1200,
  geulja: 1500,
  word: 2500,
  phrase: 4000,
};
```

For a **word**, the threshold is measured against recognition of the **whole word**, not its constituent geulja.

## What is NOT in the data model (scope fence)

- No meaning-test fields, no vocab-SRS — meaning is display-only.
- No handwriting/stroke data.
- No audio files — audio is generated on-device by TTS at runtime (see `docs/architecture.md`).
- No multi-language fields beyond `language: "ko"`. Keep the schema mono-lingual for v1; a second script would add a parallel content file later, not new per-item language fields now.
